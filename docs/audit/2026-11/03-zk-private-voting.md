# 03 — ZK private voting (governance `src/crypto/` + `packages/zk-voting-sdk`)

**What it claims to be:** "production-ready" twisted ElGamal on Ristretto255, with OR proofs, a sum proof, homomorphic tallying, threshold decryption with DLEQ proofs, and "trustless" tally verification (`README.md:24,49-54`).

**What it is:** no private vote can be cast. Committee shares fail about 94% of the time. Privacy depends entirely on keys chosen by the proposer, and nothing checks them.

**Proofs as implemented** (D = domain tag; ‖ = `hashv` concatenation):
- **OR proof.** Relation: ∃r. R = rG ∧ (C = r·pk ∨ C − wH = r·pk).
  - The SDK uses the CDS construction: e = SHA256(D‖label‖R‖C‖A0‖B0‖A1‖B1) mod ℓ with c0 + c1 = e, and emits only (c0, s0, s1).
  - The verifier recomputes A0 and B0, sets e′ = SHA256(D‖label‖R‖C‖A0‖B0) as a raw scalar, rebuilds A1/B1 with c1 = e′ − c0, and accepts only if SHA256(…‖A1‖B1) == e′.
- **Sum proof.** Chaum–Pedersen proof that log_G(ΣR) = log_pk(ΣC − wH). The algebra is correct, but the challenge is compared as raw bytes.
- **DLEQ.** Batched over 3 bases. The transcript binds every point, so special soundness holds. Only the scalar reduction is wrong.
- **Tally check.** t_k·H == C_k − Σλ_i·P_{i,k}. This is sound even with caller-chosen λ (see "Refuted").
- **Weight.** Computed on-chain (`cast_private.rs:46-51`), so voters can't encrypt a larger weight. Once the proofs are correct, each value is in {0, w} and they sum to w, so exactly one category gets w.

### ZK-01 · Critical · Confirmed · bug — The OR-proof verifier can never accept a proof, so private voting is dead
- **Where:**
  - `programs/governance-protocol/src/crypto/verify_vote.rs:77-98`
  - `programs/governance-protocol/src/crypto/types.rs:17-24`
  - `programs/governance-protocol/src/instructions/vote/cast_private.rs:15`
  - `packages/zk-voting-sdk/src/encrypt.rs:115-119,136-140`
- **Code:** `let challenge_bytes = hashv(&[DOMAIN_VOTE_PROOF, label, &r_point.0, &c_point.0, &a0.0, &b0.0]).to_bytes();` … `require!(full_hash.to_bytes() == challenge_bytes, GovernanceError::InvalidOrProof);`
- **Fails when:** every private vote.
  - Accepting requires SHA-256 of an 8-element transcript to equal SHA-256 of its own 6-element prefix, which would need a SHA-256 collision.
  - About 15 times in 16 the check fails even earlier. `PodScalar(challenge_bytes)` is not a canonical scalar, so `multiply_ristretto` returns `None`. The syscall calls `Scalar::from_canonical_bytes` (solana-curve25519 `scalar.rs:21`; agave bpf-loader `syscalls/mod.rs`).
  - **Root cause:** a CDS proof can't be checked from (c0, s0, s1) alone, because the verifier needs c1 or e, and e depends on A1/B1. The 96-byte layout can't carry enough information.
  - **Don't "fix" it naively.** Dropping the final comparison makes every check vacuous: a voter could then encrypt For = w + K and Against = −K, swinging results or making the reveal impossible.
  - Lead-verified.
  - **Reproduced by PoC:** `poc/tests/poc.rs::bug_zk01_honest_sdk_vote_is_rejected_on_chain`. 20 of 20 honest votes generated by the project's own SDK are rejected by the on-chain verifier, run natively with the same curve code as the syscalls.
- **Fix, keeping the 96-byte format:** switch both the SDK and the verifier to an AOS-chained 1-of-2 proof, with `Hs(x) = SHA256(x)` either masked (`byte[31] &= 0x0F`) or reduced mod ℓ on both sides.
  - **Verifier:**
    1. A0 = s0G − c0R and B0 = s0·pk − c0C.
    2. c1 = Hs(D‖ctx‖label‖R‖C‖0x00‖A0‖B0).
    3. A1 = s1G − c1R and B1 = s1·pk − c1(C − wH).
    4. Accept iff c0 == Hs(D‖ctx‖label‖R‖C‖0x01‖A1‖B1).
  - **Prover:** symmetric. Commit honestly on the real branch, then derive the other branch's challenge from it.
  - **Alternative:** CDS with (c0, c1, s0, s1) in 448 bytes, checking c0 + c1 ≡ Hs(…) mod ℓ. The transaction (about 1,030 B) still fits.

### ZK-02 · Medium · Confirmed · bug — The SDK reduces challenges mod ℓ but the program compares raw digests, so honest proofs pass about 6% of the time
*Downgraded from High by the verifier: an honest prover can regenerate locally with a fresh nonce until the digest is below ℓ, about 16 tries, before sending. The SDK doesn't do this today.*
- **Where:**
  - `programs/governance-protocol/src/crypto/verify_vote.rs:81,168,179-182`
  - `programs/governance-protocol/src/crypto/verify_dleq.rs:49,92-95`
  - `packages/zk-voting-sdk/src/encrypt.rs:188,205`
  - `packages/zk-voting-sdk/src/decrypt.rs:85`
- **Code:** `require!(expected_hash.to_bytes() == *challenge, …InvalidDleqProof);` on-chain, versus `Scalar::from_bytes_mod_order(hash.into())` in the SDK.
- **Fails when:** the two values match only if the digest happens to be below ℓ, which has probability ℓ/2²⁵⁶ ≈ 1/16.
  - An honest committee member's `submit_decryption_share` fails about 94% of the time, and the SDK never retries.
  - Once ZK-01 is fixed, honest sum proofs would still fail about 94% of the time.
- **Fix:** use one shared hash-to-scalar function for the OR, sum and DLEQ proofs. Either mask the top 4 bits, or add `curve25519-dalek` (no default features) on-chain and use `from_bytes_mod_order`. Compare scalars, not raw digests.

### ZK-03 · Medium (High once ZK-01 is fixed) · Confirmed · security — Privacy rests entirely on keys chosen by the proposer, and none are checked
*While ZK-01 stands, no ballot can be cast, so there is no privacy to lose yet.*
- **Where:**
  - `programs/governance-protocol/src/instructions/zk_voting/enable_private_voting.rs:16-28,34-38`
  - `programs/governance-protocol/src/constants.rs:58-59`
  - `packages/zk-voting-sdk/src/keygen.rs:28-30,47,50-58`
  - `tests/governance-protocol.ts:446,450`
- **Code:**
  - On-chain: `require!(validate_ristretto(&PodRistrettoPoint(encryption_pubkey)), …)`, then `private_config.decryption_threshold = decryption_threshold;`.
  - SDK: `(ElGamalKeypair { secret: joint_secret, public: joint_public }, shares)` and the comment `/// For additive key generation: joint_pk = pk_1 + … + pk_n`.
- **Fails when:**
  - **(a) Trusted dealer.** The SDK's only keygen is a trusted dealer that returns the joint secret. Whoever runs it can decrypt every ballot while voting is still open (C − sk·R ∈ {O, wH}).
  - **(b) Identity key.** An all-zero `encryption_pubkey` (the identity point) passes `validate_ristretto`, and the repo's own test uses it. With that key C = mH, so anyone can read every vote.
  - **(c) Mismatched keys.** `encryption_pubkey` is never checked against `committee_elgamal_pubkeys`, and mismatched keys make the reveal impossible.
  - **(d) Unchecked committee shape.**
    - Committee members may repeat.
    - `threshold` may be 0 or larger than the committee.
    - `MIN_DECRYPTION_THRESHOLD`/`MAX_COMMITTEE_SIZE` are used only in tests.
    - `committee_size > 5` panics at index 5.
  - **(e) Wrong joint key.** `compute_joint_pubkey` sums the share public keys (Σf(i)G ≠ f(0)G), which contradicts `threshold_keygen` and the Lagrange combination, so using it makes decryption fail.
- **Fix:**
  - Fix the committee key through governance in the global config, not per proposal.
  - On enable, require a non-identity key, 3 ≤ t ≤ n ≤ 5, and distinct members and keys.
  - Verify Feldman commitments: A_0 == encryption_pubkey and pk_i == Σ_k (i+1)^k·A_k (about 33k CU).
  - Replace the SDK dealer with a Pedersen DKG that never returns the joint secret.

### ZK-04 · Medium · Confirmed · security — A proposer can zero out a public vote through the reveal path
- **Where:**
  - `programs/governance-protocol/src/contexts/enable_private_voting.rs:7-12`
  - `programs/governance-protocol/src/instructions/zk_voting/aggregate_revealed_votes.rs:28-36,180-182`
  - `programs/governance-protocol/src/instructions/zk_voting/initiate_reveal.rs:5-17`
- **Fails when:**
  1. On a public proposal that already has votes, the proposer calls `enable_private_voting(size 0, threshold 0, any valid pk)`.
  2. After `end_time`, anyone calls `initiate_reveal` and then `aggregate_revealed_votes(0,0,0,[])`.
  3. That aggregate succeeds: 0 ≥ 0 shares are present, D = O, and 0·H == O − O. It writes `votes_* = 0`.
  4. A re-finalize then sets the proposal to Rejected.
- **Fix:** require `proposal.is_private_voting` in enable, `initiate_reveal` and `aggregate`, and require enabling before `start_time`. Also listed as GOV-07.

### ZK-05 · Medium · Confirmed · bug — Finalize ignores reveal state
- Duplicate of **GOV-08**. Any signer can finalize a private proposal at `end_time + 1`, before the reveal, while its votes are still 0, so it ends Rejected.
- **Fix:** require `reveal_completed` and add a reveal deadline.

### ZK-06 · Low (Medium once ZK-01 is fixed) · Confirmed · security — Ballots aren't bound to the voter or the proposal, so they can be copied
- **Where:**
  - `programs/governance-protocol/src/crypto/verify_vote.rs:77-80,90-93,174-177`
  - `programs/governance-protocol/src/crypto/verify_dleq.rs:77-90`
  - `packages/zk-voting-sdk/src/encrypt.rs:21-25`
- **Code:** `hashv(&[DOMAIN_VOTE_PROOF, label, &r_point.0, &c_point.0, &a0.0, &b0.0, &a1.0, &b1.0])`
- **Fails when:** once proofs verify, voter B, whose weight equals voter A's, replays A's three ciphertexts and 352-byte proof under B's own VoteRecord.
  - That enables ballot copying: voting like a whale without knowing the vote.
  - It also enables the Cortier–Smyth attack: k Sybil copies shift exactly one tally by k·w, revealing the target's choice at reveal time.
  - Matching a small voter's weight is cheap.
  - The weight and public key are bound implicitly through B0/B1 and C − wH. Only the voter and proposal are missing.
- **Fix:** prefix every transcript with `program_id‖proposal‖voter‖pk‖H‖w_le`, in both the SDK and the verifier. Add `proposal‖committee_index` to the DLEQ transcript.

### ZK-08 · Low · Confirmed · test-gap — No test anywhere verifies a proof
- **Where:**
  - `packages/zk-voting-sdk/src/encrypt.rs:212-225` and `packages/zk-voting-sdk/src/tally.rs:139-144`: the proof is discarded or only its length checked.
  - `tests/governance-protocol.ts:492-510`: sends all-zero proofs and expects success.

### ZK-10 · Low · Confirmed · bug — SDK key hygiene and tally bounds
- **Where:**
  - `packages/zk-voting-sdk/src/types.rs:92-96`
  - `packages/zk-voting-sdk/src/tally.rs:11-23,45-52`
  - `packages/zk-voting-sdk/src/decrypt.rs:30-48`
- **Problems:**
  - `#[derive(Debug)]` on `ElGamalKeypair { secret }` prints the secret, and nothing is zeroized.
  - Duplicate share indices make `invert(0) = 0` and silently give wrong Lagrange coefficients.
  - Using `total_private_votes` as the BSGS bound fails whenever the tally (a sum of weights up to about 666k each) exceeds the vote count.
  - There is no helper to compute the exact on-chain weight the proof must match, so a stake or score change before the transaction lands rejects the vote.

### Refuted or adjusted first-pass claims
- **"Caller-supplied Lagrange coefficients and duplicate shares let the caller forge the tally":** refuted.
  - Distinct share indices are counted through the bitmap (`submit_decryption_share.rs:37-40,77-78`).
  - Each partial is DLEQ-bound.
  - Forging t′ ≠ M would require expressing an H-component in multiples of R_k, which is the representation problem and DL-hard.
  - Bad λ values can only make the caller's own transaction fail.
- **"Transcripts don't bind the public key or weight":** partly refuted. Both are bound implicitly; only the voter and proposal binding is missing (ZK-06).

### Checked and fine
- **Encodings:** the all-zero encoding is the canonical identity point, and the add/validate handling of it is correct. The weight scalar is canonical. Ristretto has no small subgroup.
- **Constants:** `GENERATOR_H` on-chain equals the SDK's derivation, confirmed with an independent RFC 9496 implementation (`(local audit scratch file, not included)`). The basepoint constant is correct.
- **Cost:** an estimated ~105k CU for `cast_private_vote`, under 200k, with no stack warning for governance. The transaction is about 930 B.
- **SDK:** the BSGS algorithm is correct, and the SDK uses `OsRng`.
